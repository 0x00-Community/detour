# 路线

网页图层: acde 画进 detour-core 的 2D 场景 (见「接入 acde-base」), 在 Xe3 上由 detour 光栅化, **像素和 vello_cpu lowp 逐位一致**
(用户定, 2026-10-29; vello_cpu 只当对照). 没有 Xe3 的机器由 detour 回退到 vello on wgpu (`detour-fallback`, feature `fallback-vulkan`, 用户定, 2026-11-03).

做法: vello_cpu 0.3 的前端和粗光栅原样复用 (编码、条带、字形、描边、裁剪、图层、滤镜层、按行分桶; 都在 CPU 上), 只把
**细光栅** (`fine`: 逐行执行命令表, 出像素) 移植成 EU 上的 compute 着色器, 算法和 lowp 一模一样 (u8 / u16 整数, 渐变的 t 用
f32). 这样所有功能和 vello_cpu 同源, 对照只看细光栅.

```text
vello_cpu 前端 (CPU)     RenderContext: fill / stroke / glyph_run / push_layer / clip / box shadow / image
  ⇒ 条带 + 录制            strip_generator, Recorder (draws, layers, filter layers)
  ⇒ 粗光栅 (CPU)          CommandBucketer: 每行 (4 像素高) 一张命令表 render_cmds + depth_cmds, paint / layer 属性
  ⇒ 上传                  命令表、属性、alpha、编码过的 paint (渐变 u8 LUT、图片) 进 GPU 缓冲
  ⇒ 细光栅 (GPU compute)  一个线程一个 4x4 tile (SIMD16 = 16 像素): 依次执行本行和自己相交的命令; 图层栈在寄存器里;
                          lowp 的 paint / 混合 / 合成 / 遮罩逐条照搬
  ⇒ 写回                  LSC store 进目标 (linear RGBA8, 以后直接是 acde 的画布 dma-buf)
```

原来的路线 (条带实例 + 渲染管线 + 硬件混合, `detour-core` 的 raster / `Compositor`) 和 vello_cpu 差 2~3 级, 不满足逐位一致; 保留作
渲染管线的验证, 不再往上加功能.

### Apple M3 / M4 (Apple9, mlirpass `target.apple9`)

本机就是 M4 (`applegpu_g16g`). G16 的指令集没有 Mesa 模型 (GravityLinux Mesa 的 agx_apple9 只作提示), 编码在 mlirpass 里逐条上
GPU 验: 没有内核驱动, 代码放进一个 Metal binary archive 的 pipeline 里跑、读回 (mlirpass `scripts/apple9_metal.swift`). ABI:
binding 0 内存 (字节地址), binding 1 参数字 (之后是网格的工作组数), 硬件工作组 32 个调用; detour 的一个线程 (16) 两个凑一个硬件工作组.

| 阶段 | 内容 | 状态 |
| --- | --- | --- |
| M1 compute | `detour-apple-codegen::apple9`: `apple9-check` + 桥接 + mlirpass 的 `convert-gpu-to-apple9` / `apple9-regalloc` / `-control` / `-wait` | 完成 (2026-11-08, mlirpass 0.8.8): i32 / f32 (div / sqrt 正确舍入, 非规格化数冲零)、scf 控制流 (执行掩码栈)、threadgroup 内存和 barrier、内存和 threadgroup 原子与 compare-exchange、三维工作组 id 和网格大小. `tests/apple9.rs`: Intel 的 `compute/ints.mlir` 编成的机器码在 M4 上 2880 / 2880 对 (`APPLE9_METAL` / `APPLE9_DONOR`); mlirpass 的 `scripts/apple9_check.py` 七个 kernel 全对 |

IOGPU 上一次 compute 派发 (2026-11-08, macOS 15, Mac16,12; `scripts/apple-iogpu-trace.sh` 跑 mlirpass 的 Metal 运行器):

- 一个连接: `IOServiceOpen(AGXAcceleratorG16G, type 0x100005)`; 开头 struct 选择子 7 (输入 "Metal")、2、0、5、258、256、261 是
  设备信息和初始化. `IOSurfaceRoot` 另开一个 (选择子 13 / 32 / 44).
- 显存: 选择子 10 (`IOConnectCallMethod`, 104 字节进, 80 字节出): 出 `[0]` GPU 虚拟地址 (0x100_0000_0000 起;
  0x6f_0000_0000 一块), `[1]` 本进程的 CPU 映射 (0 是只有 GPU 的子分配: 输入 `[0]` 的 0x80 位, 从一块堆里切), `[3]` 高半资源号,
  `[4]` 大小. 选择子 15 (`in=[0x4000, 0 | 1]`) 映射两页内核共享的页: 命令缓冲的描述 (头、本次用到的资源号表) 和段表
  (指向缓冲绑定表等的 GPU 地址).
- 队列: 选择子 17 (`in=[0x100, 0x28]`), 通知端口 (`IOConnectSetNotificationPort` type 0), 选择子 29 / 264.
- 提交: `IOConnectTrap3(conn, 0, 队列 1, 0x38, 参数)`; 参数 56 字节, 带两个完成回调 (用户态的 block, 内核原样回传).
  用完的资源 `IOConnectTrap1(conn, 1, 资源号)`.
- 显存里: 着色器代码 (常量程序和 `_agc.main`) 在 0x100_0000_0000 那块; 两个缓冲的 GPU 地址 (binding 0 / 1) 成对写在一张表里;
  驱动生成的 USC 前导程序 (把缓冲地址装进 uniform); 一段带派发尺寸 (64 个线程, 每组 32) 的命令.
- 还要做: 逐字段弄清命令缓冲 (头、资源表、段表、派发命令、前导程序), 然后自己分配、填写、提交, 读回逐个核对.

### Apple M4 / M5 (原生, 用户定, 2026-11-04)

不走回退, 和 M1 一样原生生成命令流和着色器. 参照 (2026-11-04 查):

- 上游 Mesa (`~/coding/clone/mesa`, 10-28) 和 Asahi 内核只到 G13 / G14 (M1 / M2); M3 (G15) Asahi 能启动但没有 GPU.
- M4 唯一能照的是 GravityLinux (Asahi 的分支) 的 Mesa: `github.com/GravityLinux/mesa` `87ac51d` (MIT), 只取了
  `src/asahi` + `include/drm-uapi` 到 `~/coding/clone/gravity-mesa`; 内核是 `GravityLinux/linux` 分支 `gravity-m4`. 它把新一代叫
  **Apple9**: G16G = T8132 (M4 基础款)、G17P = T8140 (变体报 'P'); generation 15 照 G14 走. uAPI 还是 asahi 的, 只多一个
  `DRM_ASAHI_FEATURE_FRAGMENT_BARRIER` / `DRM_ASAHI_RENDER_VDM_BARRIER_FRAGMENT`.
- Apple9 和 AGX2 的差别 (照 GravityLinux 读的, 没验): 指令编码不同 (`compiler/agx_apple9_encoding.h`、`agx_apple9_machine.c`),
  着色器从固定 USC 基址的入口表进 (`lib/agx_device.c` 的 `fixed_apple9_usc_base`、`AGX_APPLE9_RENDER_CONTEXT_BASE`),
  VM 布局另排. 它的图形路径里 launcher / helper / 清屏的程序还是从 Metal 抓的不透明二进制 (`drm-shim/README.m1n1-g16g.md`),
  不能照抄 (来源和许可), 要自己从编码生成.
- 不收的参照: `ADevWithAnIdea/agx-re` (代码 GPL-3.0、文档 CC-BY-NC-SA) 和 `Ghost-Silver/asahi-g16-toolkit` (自称 G16 = M3,
  和 GravityLinux 对不上) 只读不抄.
- M5: 没找到任何公开的 GPU 资料 (generation、ISA、命令流都不知道).

## 接入 acde-base

- 2D 场景 (用户定, 2026-11-03): detour-core 的 `PaintScene` / `Scene` / `Filter` 取代 anyrender, blitz-paint 和 acde 的
  crates/render 直接画进它. detour 负责把它画出来: Xe3 上走自己的光栅 (R2–R6), 别处走 `detour-fallback` (vello on wgpu on Vulkan); 关掉 `fallback-vulkan` 时驱动做不了的直接 panic.
  步骤: S1 场景类型进 detour-core、`VelloScene` (完成); S2 acde 换掉 anyrender / anyrender_vello, 画面不变;
  S3 acde crates/paint 的光栅和合成 (vello 渲染、图层合成、滤镜、dma-buf 画布) 搬进 detour, acde 只交场景和目标;
  S4 Xe3 的光栅接在同一个接口下面.
- detour 作为 crate 链接进 acde (git 依赖, 不拷进 acde-base, 见 AGENTS.md), 实现 crates/acde `webgpu/`
  现在用 wgpu 实现的那一层, acde-dom 的 `GpuNative` 契约不变. WebGPU 跑在页面所在的 web 线程上: 命令编码在 CPU 上很便宜,
  GPU 异步执行; 要同步答案的 (`mapAsync`、`onSubmittedWorkDone`、canvas 的 `toDataURL` ...) 等对应的 syncobj.
- 上屏: canvas 的 `webgpu` 上下文画进一组导出成 dma-buf 的缓冲 (交换链), 每帧把 dma-buf 和 acquire fence (sync_file)
  交给合成器合成, 不经 CPU 拷贝, 不经 wgpu.
- 没有 Xe3 核显 (虚拟机、其他厂商的 GPU) 时 `navigator.gpu` 照旧走现有的 wgpu 实现.
