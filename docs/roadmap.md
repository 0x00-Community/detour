# Roadmap

Web layer: acde paints into detour-core's 2D scene (see "Plugging into acde-base"); on Xe3 detour rasterizes it, **pixels bit-identical to vello_cpu lowp**
(user's decision, 2026-10-29; vello_cpu is only the reference). Machines without Xe3 fall back in detour to vello on wgpu (`detour-fallback`, feature `fallback-vulkan`, user's decision, 2026-11-03).

Approach: reuse vello_cpu 0.3's front end and coarse rasterizer as is (encoding, strips, glyphs, strokes, clipping, layers, filter layers, per-row bucketing; all on the CPU), and port only
**fine rasterization** (`fine`: execute the command list row by row, output pixels) to a compute shader on the EU, with exactly the same algorithm as lowp (u8 / u16 integers, gradient t in
f32). So every feature shares its source with vello_cpu, and the comparison only concerns fine rasterization.

```text
vello_cpu front end (CPU)  RenderContext: fill / stroke / glyph_run / push_layer / clip / box shadow / image
  ⇒ strips + recording       strip_generator, Recorder (draws, layers, filter layers)
  ⇒ coarse raster (CPU)      CommandBucketer: one command list per row (4 pixels high) render_cmds + depth_cmds, paint / layer attributes
  ⇒ upload                   command lists, attributes, alpha, encoded paints (gradient u8 LUT, images) into GPU buffers
  ⇒ fine raster (GPU compute) one thread per 4x4 tile (SIMD16 = 16 pixels): runs in order the commands of its row that intersect it; layer stack in registers;
                          lowp paint / blend / composite / mask copied one by one
  ⇒ write back               LSC store into the target (linear RGBA8, later directly acde's canvas dma-buf)
```

The original route (strip instances + render pipeline + hardware blending, `detour-core`'s raster / `Compositor`) differs from vello_cpu by 2~3 levels, so it is not bit-identical; it is kept as
validation of the render pipeline, and no more features are added on top of it.

## Multiple vendors: one MLIR

The core of detour is generating each vendor's GPU binaries (commands and machine code) directly with mlirformat / mlirpass, all GPUs going through the same system (user's decision, 2026-10-30), not
building a compatibility layer. The kernel interfaces (`crates/<vendor>/<kernel driver>`) are only thin pipes that hand the generated images to the kernel; the work is in the dialects and passes:

- Vendor-independent, in `detour-core`: the image container dialect `image.*` (memory / stream / kernel / data), addressing `Layout` and output `ImageEmit`
  (vendors implement `ImageTarget`: how the command stream ends, how kernels are encoded, how state is packed); table-driven packing and templates (`Layouts::pack` / `Template`);
  attribute construction `A`; register allocation `LinearScan` (vendors implement `RegTarget`: register file, value size and alignment, precoloring). These have been lifted up
  (2026-10-30); Intel is the first `ImageTarget` (`Xe3`) and `RegTarget` (`GrfFile`), AMD / Apple hook in once their shader lowering is done.
- Each vendor only writes: the command / state tables (Intel genxml, AGX `cmdbuf.xml`, AMD `registers/*.json` + `pkt3.json`, one front end each in the generator),
  the instruction dialect and encoding (`xe3.eu` / AGX USC / RDNA), wait insertion (SWSB / AGX wait / `s_waitcnt`), `convert-detour-to-<vendor>`.

### Apple M3 / M4 (Apple9, mlirpass `target.apple9`)

The local machine is an M4 (`applegpu_g16g`). There is no Mesa model of G16's instruction set (GravityLinux Mesa's agx_apple9 only serves as hints); encodings are verified one by one on the
GPU in mlirpass: there is no kernel driver, so the code is put into a pipeline in a Metal binary archive, run, and read back (mlirpass `scripts/apple9_metal.swift`). ABI:
binding 0 is memory (byte addresses), binding 1 the parameter words (followed by the grid's workgroup counts), hardware workgroups have 32 invocations; two detour threads (16 each) make up one hardware workgroup.

One compute dispatch on IOGPU (2026-11-08, macOS 15, Mac16,12; `scripts/apple-iogpu-trace.sh` running mlirpass's Metal runner):

- One connection: `IOServiceOpen(AGXAcceleratorG16G, type 0x100005)`; the struct selectors 7 (input "Metal"), 2, 0, 5, 258, 256, 261 at the start are
  device info and initialization. `IOSurfaceRoot` opens another one (selectors 13 / 32 / 44).
- Video memory: selector 10 (`IOConnectCallMethod`, 104 bytes in, 80 bytes out): output `[0]` is the GPU virtual address (starting at 0x100_0000_0000;
  one block at 0x6f_0000_0000), `[1]` this process's CPU mapping (0 for a GPU-only suballocation: the 0x80 bit of input `[0]`, carved out of a heap), `[3]` the upper-half resource id,
  `[4]` the size. Selector 15 (`in=[0x4000, 0 | 1]`) maps two pages shared with the kernel: the command buffer's descriptor (header, table of the resource ids used this time) and the segment table
  (GPU addresses pointing to the buffer binding table etc.).
- Queue: selector 17 (`in=[0x100, 0x28]`), notification port (`IOConnectSetNotificationPort` type 0), selectors 29 / 264.
- Submission: `IOConnectTrap3(conn, 0, queue 1, 0x38, args)`; the args are 56 bytes, with two completion callbacks (user-space blocks, passed back unchanged by the kernel).
  Resources that are done: `IOConnectTrap1(conn, 1, resource id)`.
- In video memory: the shader code (constant program and `_agc.main`) is in the 0x100_0000_0000 block; the GPU addresses of the two buffers (binding 0 / 1) are written as a pair in a table;
  a driver-generated USC preamble program (loads the buffer addresses into uniforms); a command carrying the dispatch size (64 threads, 32 per group).
- Still to do: understand the command buffer field by field (header, resource table, segment table, dispatch command, preamble program), then allocate, fill in and submit ourselves, read back and check value by value.

## Plugging into acde-base

- 2D scene (user's decision, 2026-11-03): detour-core's `PaintScene` / `Scene` / `Filter` replace anyrender; blitz-paint and acde's
  crates/render paint directly into it. detour is responsible for drawing it: on Xe3 through its own raster (R2–R6), elsewhere through `detour-fallback` (vello on wgpu on Vulkan); with `fallback-vulkan` off, whatever the driver cannot do panics directly.
  Steps: S1 scene types into detour-core, `VelloScene` (done); S2 acde replaces anyrender / anyrender_vello, picture unchanged;
  S3 the raster and compositing of acde crates/paint (vello rendering, layer compositing, filters, dma-buf canvas) move into detour, acde only hands over scenes and targets;
  S4 Xe3's raster plugs in under the same interface.
- detour is linked into acde as a crate (git dependency, not copied into acde-base, see AGENTS.md), implementing the layer that crates/acde `webgpu/`
  currently implements with wgpu; acde-dom's `GpuNative` contract is unchanged. WebGPU runs on the web thread that hosts the page: command encoding is cheap on the CPU,
  the GPU executes asynchronously; whatever needs a synchronous answer (`mapAsync`, `onSubmittedWorkDone`, canvas `toDataURL` ...) waits on the corresponding syncobj.
- Presentation: the canvas's `webgpu` context paints into a set of buffers exported as dma-bufs (swapchain); each frame the dma-buf and the acquire fence (sync_file)
  are handed to the compositor to composite, with no CPU copy and not through wgpu.
- Without an Xe3 iGPU (virtual machines, other vendors' GPUs), `navigator.gpu` goes through the existing wgpu implementation as before.
