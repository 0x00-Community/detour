# The xe3 dialect and Xe3 hardware

## Dialect

- Each genxml instruction / struct / register is an op with only attributes: `xe3.cmd.<name>` / `xe3.state.<name>` / `xe3.reg.<name>`, the name is
  the lowercase underscore form of the genxml name (`3DSTATE_VS` ⇒ `xe3.cmd.3dstate_vs`), fields are attributes of the same name (lowercase underscore, prefixed with `_` if they start with a digit). Default =
  genxml's default. Struct fields are dictionaries, fixed-length arrays are arrays (nested for multiple dimensions), variable-length groups are `elements = [{...}, ...]`. If `dword_length` is not written it is computed from
  the packed length (variable-length groups, long forms beyond the declared length). Table-driven packing (`pack.rs` in detour-core), the tables are generated by `scripts/intel-cmdgen.py` from `crates/intel/dialect/genxml/xe3.xml`
  (`python3 scripts/intel-cmdgen.py crates/intel/dialect/genxml/xe3.xml crates/intel/dialect/src/cmd.gen.rs`). xe3.xml is Mesa's
  `src/intel/genxml/xe3.xml` together with the xe2 / gen125 / ... it imports, flattened with `genxml_import.py --flatten` (MIT, Intel). Video engine ones are not generated.
- Oracle: `tests/oracle.mlir` has one pseudo-random value per field per entry (the same values the Mesa C pack functions got back then), `tests/oracle.expected` is what Mesa packed;
  290 entries bit-identical. Intentional difference from Mesa: alternative address fields starting at the same dword are ORed (Mesa takes only the last one).
- `xe3.eu.<mnemonic>`: one EU instruction. Operands are string attributes in gentool syntax (`dst = "r10<1;1,0>:f"`, `src1 = "-r12<1;1,0>:f"`,
  immediates `"0x3f800000:f"`), the rest see `asm.rs`. Before register allocation operands can be SSA values (types `!xe3.grf<f32>` etc., one SIMD16 register),
  empty source slots are filled in order; `xe3.eu.payload {grf}` is a value already in registers when the thread starts. Oracle: the comment above each one in `tests/eu.mlir` is gentool assembly,
  `tests/eu.expected` is what `gentool asm -p ptl` assembled (regenerate with `scripts/intel-eu-oracle.sh`); 67 instructions bit-identical.
- Finishing (`xe3-pad`, `xe3-end`): kernels carry `pad = 128` (128 zero bytes appended; the EU prefetches past the end); at the end of each batch
  `xe3.cmd.mi_batch_buffer_end` is added, plus `xe3.cmd.mi_noop` if the total length is odd. Output only packs op by op, adding nothing on its own.
- Placement (`xe3-layout`): memory starts at 1 MB, 64 KB aligned (can be raised with `align`); items are laid out by `align` (default 64). Symbols in attributes: `@x` is x's GPU
  address, `@m::@x` is x's offset within memory m, `[@x, n]` is x's address plus n. All state base addresses are 0, pointers are GPU addresses
  (must be below 4 GB); binding table pointers are offsets within the pool.

## Pitfalls

- Reaching the fence after submission does not mean the job finished: xe signals anyway when the job errors or hangs. To know it finished, check `Queue::fault()` (`Device::run` already does).
- On GPU hang / page fault: `journalctl -k` has the faulting address and engine. To locate which command it gets stuck on: insert `xe3.cmd.mi_store_data_imm` markers in the batch and read them back;
  then bisect by disabling stages.
- Binding tables can only live in the binding table pool (the size in `3DSTATE_BINDING_TABLE_POOL_ALLOC` is in 4 KB units); table pointers beyond the pool wrap around;
  every stage must send a binding table pointer (stages that bind nothing get a table whose entry 0 is a null surface). From Xe-HP on there is no `3DSTATE_PUSH_CONSTANT_ALLOC_PS`.
- The address in `STATE_SYSTEM_MEM_FENCE_ADDRESS` must be 4 KB aligned.
- The source of an EOT message must be in r112 ..= r127.
- When gentool reads the cache suffix of `load_block2d` it looks in the store name table (load's L1C_L3C = 8 is written `wt.wb`).
- Custom forms mlirformat does not recognize (`vector.shuffle`, all of spirv) are written in generic form. The custom form of `vector.from_elements` can be read from 0.5.0 on.
- ⚠ At thread start f32 denormals are flushed to zero (cr0 bit 7 = 0); every kernel's prologue sets it. f32 texels returned by the sampler always have denormals flushed to zero.
  The EU has no f32 division or exact square root, only approximate inv / rsq: both are corrected to correct rounding. Details in section 1 of [optimizations.md](optimizations.md).
- ⚠ A send's destination register must not overlap its payload (Mesa's register allocation makes the two interfere); when they overlap the readback is randomly wrong.
- ⚠ Software scoreboard: read-after-write across pipes must also wait (the int pipe has not read yet when the float pipe writes); when RegDist and SBID are combined on one instruction there is no pipe number
  (inferred from the source type), only specific combinations can be combined; having waited on `$n.src` does not mean the result has arrived. See section 2 of [optimizations.md](optimizations.md).
- ⚠ Someone else's dma-buf (udmabuf and the like, an sg buffer object in xe) can only be bound into the VM with a coherent PAT (`MemType::Coherent`, PAT 1); with a non-coherent one
  (`Streaming`, PAT 0) vm_bind returns EINVAL. `Context::import_canvas` uses Coherent (`compose` example: the udmabuf canvas matches byte for byte).
- ⚠ Compute shaders take at most 8 parameters (`COMPUTE_PARAMS`); exceeding it reports "failed to legalize operation 'func.func'" (if any entry point in the same module exceeds it, compiling any entry point reports it). Private functions with `i1` parameters do not compile either; expand with select.
- ⚠ SCISSOR_RECT must be 64-byte aligned (Wa_1409725701, anv); with 32-byte alignment nothing draws when the scissor test is on.
- ⚠ sRGB format conversion is approximate (within D3D tolerance, not equal to the exact value of the transfer function): decoding the 256 bytes is off by at most 0.29 of a byte step (1.1e-3 at 194), encoding linear 0.5 gives 187 (formula 188), 20 of 256 values are off by 1 (`formats` example). Things that need bit-exact comparison should not go through sRGB formats.
- ⚠ Cube sampling: the sampler first clamps the direction coordinates to −1 ..= 1 and then picks the face, so the direction must first be divided by the absolute value of its largest component (`detour-normalize-cube`); (3, 2.25, 2.25) without the division lands on a corner of +z.
- ⚠ Xe2 Tile64 multisampled tiles (32-bit texels): 2x is 64 wide × 128 high (not 128 × 64), 4x 64 × 64, 8x 64 × 32 (isl's swizzle: U 8 bits, V 7 / 6 / 5 bits); when the size is computed wrong the last row of tiles runs past the buffer and draws elsewhere.
- Alpha to coverage (dither off): covers ceil(alpha · n − 1/2) samples (measured by sweeping 257 alpha values at 4x / 8x each).
- Compute workgroup IDs: x in r0.1, y in r0.6, z in r0.7 (Mesa `emit_work_group_id_setup`).
- ⚠ Byte-to-float `mov :f ← r.k<32;8,4>:ub` is only legal for k = 0 (for a float destination the source region must keep the lowest channel's bit position, gentool validation errors);
  other bytes are first converted to `:d` (`detour.unpack4xu8`).
- ⚠ There is no 32 × 32-bit integer multiply (`mul :d :d` is wrong on odd channels, can cause out-of-bounds writes and CAT errors); `cmp` cannot mix integer sources with a float destination
  (the destination register is not written). See [optimizations.md](optimizations.md) 1.5.

## Xe2 / Xe3 fragment shader payload and interpolation (after Mesa brw)

Intel has not published a PRM for Xe2+; the following is read from Mesa's compiler (paths relative to `~/coding/mesa/src/intel/compiler/brw`), follow it when implementing varyings:

- PS SIMD16 payload (`brw_thread_payload.cpp` `setup_fs_payload_gfx20`): r0 thread header, r1 masks and pixel coordinates; then 2 registers for each barycentric kind enabled by `3DSTATE_WM`'s
  Barycentric Interpolation Mode (b.x one for 16 channels, b.y one); further on optional source depth, source W,
  coverage mask, etc. After the payload (`dispatch_grf_start_register_for_constant_setup_data_0`) come the attributes' plane parameters.
- Plane parameters (`brw_compile_fs.cpp` `remap_attr_reg`): Gfx20+ uses 12 bytes per scalar component (a0, a1-a0, a2-a0), every 5 components packed into one 64-byte register;
  component i is at byte (i % 5) * 12 of register i / 5 of the setup area.
- Interpolation: Xe2+ has no PLN (`gen_validate.cpp`: "PLN is Gfx9 only"), Mesa first turns it into two FMAs in NIR (`nir_lower_interpolation.c`).
  ⚠ Correspondence verified on real hardware (`varying` example): `v = b.x * (a1 - a0) + a0`, then `v = b.y * (a2 - a0) + v` (b.x in r1, goes with vertex 1;
  b.y in r2, goes with vertex 2). Reading that Mesa NIR literally swaps b.x / b.y.
- Our implementation (`shader.rs` `Interpolate` and `place_arguments`): enable bit 0 of `3DSTATE_WM`'s Barycentric Interpolation Mode
  (perspective pixel), the PS setup data starts at r3 (`dispatch_grf_start_register_for_constant_setup_data_0 = 3`), 4 components per varying.
- Vertex shaders write the VUE (`brw_lower_logical_sends.cpp` `lower_urb_write_logical_send_xe2`): an LSC URB store, the address is the URB handle (r1),
  data laid out by component; the VUE holds the header (4 dwords), the position, then one vec4 per output (16 bytes per slot). Xe2+ URB offsets are in bytes, an immediate offset on a FLAT address,
  placed in extended descriptor bits 31:12 (`gen_lsc_ex_desc_encode`): the k-th varying is at 32 + 16k. We emit one non-EOT URB write per varying (taking an SBID),
  and a final EOT write for the header and position.
- SBE (`iris_emit_sbe`): read offset 1 (256 bits, skipping the header and position), read length ceil(n / 2), `number_of_sf_output_attributes = n`; in `3DSTATE_SBE_SWIZ`
  the i-th attribute's source_attribute = i (default all 0: every attribute reads the 0th varying). Currently at most 2 varyings.
- ⚠ The VS URB entry first holds the vertex fetched by VF (one vec4 per input), then the VS writes the VUE into the same entry: the entry size in `3DSTATE_URB_ALLOC_VS`
  (in 64-byte units, minus 1) must fit max(input count, 2 + varying count) vec4s. The default 0 only fits 4: with 5 inputs the vertex spills into the adjacent entry, and other vertices' / instances'
  attributes read back wrong, with no error at all (measured on this machine, when adding paint attributes to `strips`). When entries get bigger the entry count shrinks proportionally (multiple of 8), `render.rs` `draw`.

## Texture sampling (after Mesa brw)

- `detour.sample` ⇒ SAMPLE_LZ (message type 24, level 0, no derivatives), SIMD16 (Xe2's simd_mode 1), headerless (`lower_sampler_logical_send`):
  payload u and v one register each, r, g, b, a come back as four. Descriptor `gen_sampler_desc_encode` (same as `msg::Sampler`). When headerless, the sampler state
  pointer comes from `3DSTATE_SAMPLER_STATE_POINTERS_PS`.
- Mipmapped textures (linear): isl's GFX4 2D layout (level 0 on top, level 1 below, level 2 to the right of level 1, then each following one below), aligned to 128 bytes × 4 rows (Xe2+ linear surfaces
  HALIGN_128 / VALIGN_4, isl_gfx12 / gfx20 choose_image_alignment_el); no mip tail (MipTailStartLOD = 15). Single-level textures are still tightly packed at `width * 4`
  (render targets and the compositor's dma-bufs are like that). Sampler: MIPFILTER, LOD 0 ..= 14, CLAMP_MODE_OGL (iris).
- Binding table: entry 0 is the render target, texture b is entry 1 + b, sampler state b. `3DSTATE_PS`'s binding_table_entry_count = 1 + n,
  sampler_count = ceil(n / 4).
- SAMPLER_STATE after iris `iris_create_sampler_state`: clamp, address rounding enabled when linear, border color pointer pointing at a zeroed SAMPLER_BORDER_COLOR_STATE.
- `detour.sample` is SAMPLE (message type 0, level picked from the derivatives of the 2x2 block, WGSL `textureSample`), not SAMPLE_LZ; single-level textures still take level 0.
- ⚠ **Sampling needs Vector Mask** (measured on this machine, 2026-11-03): when a fragment shader samples, 3DSTATE_PS's Vector Mask Enable must be on. With the dispatch mask,
  helper pixels in 2x2 blocks cut by a triangle edge do not execute (their uv are leftover register values), the derivatives are wrong, and on the diagonal levels 6 ~ 8 get picked (`mipmap` example 928 wrong);
  with it on it is correct. Render target writes still only write covered pixels (red and green triangles sharing an edge, the later one's helper pixels do not cover the earlier one, 0 wrong). Mesa on XeHP+ only enables VMask for coarse /
  wide subgroups; here we differ from it, real hardware is authoritative. Note: with it on, helper pixels also execute buffer stores (Mesa masks them off with a sample-mask predicate, we have not done that yet),
  so stores in fragment shaders that sample write extra.
- Sends with a return are out of order: take an SBID, instructions using the result wait on `$n.dst` (`xe3-swsb`); the result occupies 4 consecutive registers (`xe3-regalloc`).

- **Compute-only frames have no binding table pool**: 3DSTATE_BINDING_TABLE_POOL_ALLOC used to be sent only with draws; the compute interface
  descriptor carries a binding table pointer (an offset in the pool), but when the frame has no draw the pool is not set, and the first TGM message GPU faults (2026-11-04).
  Before a compute walker with a binding table, send the pool once (`Cmds::compute_bound`).
- **Storage textures use TGM typed messages** (Mesa brw `lower_lsc_surface_logical_send`): SFID TGM, LOAD_CMASK / STORE_CMASK,
  BTI addressing (extended descriptor 31:24), A32, D32, cmask is all ones in the low bits for the channel count; 2D is two coordinates u, v, one register each (SIMD16; from Xe2 on not split into
  SIMD8), data separately in src1. Writes outside the surface are dropped by the data port; format conversion (float → unorm etc.) is done by it too.

- **The destination of integer vector immediates (`:v` / `:uv`) must be word**: `mov r<1>:d 0x44440000:uv` does not error but every channel gets 0 (sample_index
  at first got the numbers of the adjacent slot everywhere). Following Mesa, compute the whole thing in packed words (`dst_as = "uw"` / `as = "uw"`), then widen to dword at the end
  (`packed0`).

- **Dual-source RT writes are SIMD16 on Xe2+**: only SIMD32 is not allowed (Mesa brw_lower_simd_width; the SIMD8 split is Gfx12 and earlier). The message
  control is 2 (the name SIMD8_DUAL_SOURCE_SUBSPAN01), not 1 (SIMD16_SINGLE_SOURCE_REPLICATED: giving it an 8-register
  payload GPU faults).

## Blending

- Blending belongs to the pipeline (`blend = "premultiplied"`): BLEND_STATE plus one BLEND_STATE_ENTRY (back to back), color and alpha both ONE / INV_SRC_ALPHA / ADD;
  `3DSTATE_PS_BLEND` with the same factors (iris's PS_BLEND matches entry 0). With blending on, dither is turned off (iris follows GL's dither, which GL enables by default):
  dither adds noise to unorm8 results.
- ⚠ Blending arithmetic (measured on this machine, `strips` example): for unorm8 targets, the shader output is first rounded to unorm8, then `src + dst * (255 - src.a) / 255`
  is rounded back to unorm8, quantizing once per layer drawn. Compared per channel with this model (f64), 92% are equal, and all the rest that differ by 1 are cases where some rounding in the model falls near .5 (within 0.01):
  the GPU's own conversions (unorm8 → float, multiply) are not exact f64, which only shows at the boundaries. So compared with renderers that "quantize only once at the end" (vello_cpu's f32
  pipeline), places with many layers can differ by up to 2.

## References

Intel has not published a PRM for Xe3. Register and command layouts come from Mesa's genxml; instruction encoding and how pipeline state is written follow Mesa's
`src/intel/compiler/gen` (encoder / assembler / disassembler), `compiler/jay` (the new compiler for Xe2 / Xe3), `vulkan` (anv), `blorp`.
A local copy of Mesa (`~/coding/mesa`, shallow clone) is for reference only, not part of the build, read-only; how to search it: see [.skills/detour-mesa](../.skills/detour-mesa/SKILL.md).

- **z convention** (2026-11-03): viewport m22 = 1, m32 = 0, 3DSTATE_CLIP API Mode = D3D: NDC z ∈ [0, 1] is the depth (WebGPU / Vulkan; anv when
  `depth_clip_negative_one_to_one` is false). Previously GL's m22 = m32 = 0.5. A clear triangle at depth 1.0 is on the far plane and is not clipped away by z (verified with the `depth` example).
- **Depth surfaces are Tile4**: 3DSTATE_DEPTH_BUFFER's Tiled Mode only has TILE64 / TILE4; pitch aligned to 128 bytes, rows to 32; with a depth surface
  Depth Write Enable is always true (isl_emit_depth_stencil_hiz_s), the real write switch is in 3DSTATE_WM_DEPTH_STENCIL.

- **MSAA surfaces can only be Tile64** (isl_gfx20 filter_tiling: RENDER_SURFACE_STATE::NumberofMultisamples can be greater than 1 only when Tile Mode = Tile64).
  Xe2's Tile64 encodes the sample index into the in-tile address (`xe2_tile64_2d_32_16bpp_4msaa_swiz`: V5 V4 U7 U6 V3 V2 S1 S0 U5 U4 V1 V0 U3 U2 U1 U0):
  for 32-bit pixels at 4x one 64 KB tile is 64 × 64 pixels × 4 samples, physically 256 bytes × 256 rows. MSAA surfaces are not read on the CPU (read the resolve), only the size,
  row pitch and surface fields need to be right.
- **LD2DMS_W only takes 16-bit parameters** (gfx12.5+, Mesa brw_lower_logical_sends.cpp: "ld2dms_w SIMD8H and SIMD16H Only"): SIMD Mode uses
  SIMD16H (5), each parameter (sample index, MCS 0..3, u, v) takes one GRF, the 16 channels' 16-bit values in its low 32 bytes. Given 32-bit parameters the sampler reads them
  as 16-bit and the positions it reads are scrambled (2026-11-03 on the board: triangle scaled up 2x, every other column wrong).
- **Control flow is structured after Mesa** (brw_to_binary.cpp / gen_control_flow.cpp): `(f0.0) if` / `else` / `endif`, loops have no DO instruction,
  `(f0.0) break` lets finished channels leave, `while` jumps back to the loop head; JIP / UIP are byte counts from the instruction itself (16 per instruction): if with else has JIP to
  else + 1, UIP to endif; else has both to endif; endif's JIP goes to the end of the enclosing scope (the enclosing else / endif / while), or the next instruction if there is no enclosing scope;
  break's UIP goes to the while, JIP to the end of the innermost scope; while's JIP goes back to the loop head (negative). 2026-11-03 on the board: per-channel differing conditions and counts are all correct.
- **The BLEND_STATE entry for MRT is selected by the RT write message's Render Target Index**, not the binding table index: on Xe2+ in extended descriptor bits 24:21
  (Mesa lower_fb_write_logical_send: `ex_desc = target << 21`). If unset, every target uses entry 0 (2026-11-03 on the board: the second target's result
  was exactly entry 0's write mask and no blending).
- **Packing dwords into words cannot be `mov r<1>:uw r:d`**: the region rules require the destination stride to equal the ratio of execution type size to destination type size (here 2), the hardware writes with stride 2,
  odd channels wrong. Following Mesa, write it as a same-type word move, the source taking the low half of each dword: `mov r<1>:uw r<16;8,2>:uw`.
