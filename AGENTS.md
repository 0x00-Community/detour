# detour

Our own user-space GPU display driver: it does not go through Mesa, Vulkan, OpenGL or libdrm. Command buffers, state and shader machine code are all
generated by detour itself and submitted directly through the kernel GPU driver's ioctls. Everything is Rust. The goal is to beat Mesa: a shorter path (no GL / Vulkan state
machine and no driver-layer guessing; every command and every state bit is ours), and higher performance.

Every acde window uses it: rasterization of the web layer (today vello → wgpu → Vulkan → Mesa) and WebGPU in web pages (`navigator.gpu`,
the `webgpu` context of `<canvas>`) must all go through detour. Optimized only for Intel Xe3 (Panther Lake); the implementation follows Mesa's iris (OpenGL) and
anv (Vulkan) (`~/coding/mesa`). acde-base's WebGPU currently goes
wgpu → Vulkan → Mesa (ANV), with acde-dom calling crates/acde `webgpu/` through the `GpuNative` contract (acde-dom `src/native.ts`);
detour replaces the whole wgpu / Vulkan / Mesa stretch under the same contract. Both the WebGPU render and compute pipelines live here.
canvas 3D (user's decision, 2026-11-03, overturning the earlier "no WebGL"): all three `<canvas>` contexts `webgl` / `webgl2` / `webgpu` are
implemented by detour (what the driver cannot do goes to the Vulkan fallback), and 3D must be well supported. WebGL is a GLSL ES frontend + GL state machine semantics mapped onto detour's pipelines.
Scope (user's decision, 2026-11-03): not just 2D. **Whatever Vulkan can do, detour must be able to do** -- the complete 3D graphics pipeline and compute, with Vulkan's
full capability set as the reference (see docs/roadmap.md "3D: everything Vulkan can do"); 2D scenes are just one user. But the Vulkan API itself is not implemented: capabilities match,
the interface is our own (the MLIR `detour` dialect + runtime). GPU only; NPU is not here (separate project, do not touch).

Purpose (user's decision, 2026-10-30): use the mlirformat / mlirpass stack to directly generate each GPU vendor's operator binaries (command streams and shader machine code); all GPUs
go through the same system, not a compatibility layer. Each vendor's kernel interface is just a thin pipe that hands the generated image to the kernel; the dialects and passes are the main body (see docs/roadmap.md
"Multiple vendors: one MLIR").

detour is a standalone repository; no other repository keeps a copy of it (user's decision, 2026-11-02). acde-base depends on it as a Rust crate (git dependency on
`AC/detour` on `gitea.dopamine`, pinned rev; user's decision, 2026-11-03; no longer pushed to GitHub since 11-12), not copied into `vendors/`. The interface belongs to detour (user's decision, 2026-11-03):

- acde's web layer only knows detour-core's 2D scene (`PaintScene` / `Scene` / `Filter`, `crates/core/src/scene.rs` / `filter.rs`):
  blitz-paint and acde's crates/render paint directly onto it, with no anyrender layer in between.
- The fallback belongs to detour, not acde: with Xe3, detour's own rasterizer is used; without it (virtual machines, other GPUs, debug mode on Windows / macOS) it goes to
  `detour-fallback` (feature `fallback-vulkan`, on by default; vello on wgpu on Vulkan). Who does the work is decided by `detour::Backend::pick`, not chosen by acde;
  with `fallback-vulkan` off, anything the driver cannot do panics directly, no silent downgrade.
  Feature `compiler` (on by default, implied by every driver) is the compiler, image, pack, regalloc, raster and kmd in base (MLIR, vello_common);
  with it off, detour only has the 2D scene / filter / compositing types (and the fallback if on), without mlirformat (and its jemalloc); acde depends on it this way on Windows / macOS. The fallback's device prefers a real GPU (`Device::open`, only takes lavapipe when there is none); pages also have `Device::open_hardware` (real GPUs only).
  Without a real GPU, pages are painted directly by the CPU (`CpuRaster`, `src/cpu_raster.rs`, xe3 + Linux: vello_cpu rasterization, compositing done on the CPU following `compose.wgsl`,
  written directly into the mapped dma-buf canvas; `PageRaster::cpu()`, a kind of `Painters` alongside Vulkan / Xe3, not a Vulkan fallback), never opening a Vulkan device
  (user's decision 2026-11-14: lavapipe crashes on a null pointer when exporting sync_file; dragging a window in a VM gives SIGSEGV). Blur is three box-blur passes approximating a Gaussian (the GPU uses dual Kawase); it looks the same, the bytes differ.

acde-base once kept a copy at `vendors/detour` (2026-10-29 to 11-02, crates/paint `detour.rs`, last version `7b9181d`); it has been deleted, and the changes on that copy
were moved back here. detour does not commit into other repositories.

## Vendors

One directory per vendor, crate names carry the vendor: `crates/intel/*` is `detour-intel-*`, `scripts/intel-*`.
To change platform (e.g. AMD integrated graphics, kernel driver amdgpu), add a `crates/amd/` group without changing Intel's. The vendor-independent parts (kernel interface traits,
the detour dialect with WebGPU semantics, the shader frontend) live in `crates/core` (one crate, `detour-core`); vendor backends implement their interfaces (the kmd traits, lowering of the dialect).

Currently supported: Intel Xe3 integrated graphics (Panther Lake, e.g. the Intel Graphics of Core Ultra 7 356H, PCI 8086:b0a0, kernel driver xe). The second vendor,
Apple M1 (AGX G13, Asahi Linux, kernel driver asahi), is in progress: `crates/apple/*`, progress in phase A of [docs/roadmap.md](docs/roadmap.md)
(Apple M3 / M4 compute is in `detour-apple-codegen::apple9`, mlirpass's Apple9 target, verified on the local M4);
reference is Mesa's asahi (`src/asahi`, read-only; that directory does not accept AI-written changes, we only read and never submit). Other GPUs are out of scope.

## Hard rules

- ⛔ Deployed ≠ success: it only counts when pixels / read-back numbers match one by one (see CONTRIBUTING).
- ⛔ No MLIR on the per-frame path: MLIR runs only when building pipelines / compiling.
- ⛔ No hand-written packing or encoding: generated from genxml, checked bit by bit against Mesa / gentool.
- Optimize only for Xe3; hardware details follow Mesa (`~/coding/mesa`, read-only), with sources cited.
- Push only to origin, and only with the user's consent.
